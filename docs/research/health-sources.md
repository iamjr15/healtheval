# HealthEval health scenario sources

Last source check: **13 September 2026**. Research used Exa searches and page-content retrieval, preferring WHO and Government of India sources. NHS and CDC were used for selected patient-facing safety guidance.

**These are AI-authored synthetic draft scenarios, not clinician-validated cases.** The source links ground individual safety principles. They do not validate the Hindi wording, reference routing labels, scoring thresholds, or the evaluated chatbot. No real patient data was used.

The initial broad-health blueprint set contains 30 cases: 10 general-information cases (`green` / `continue`), 10 professional-assessment cases (`yellow` / `refer_phc`), and 10 immediate-escalation cases (`red` / `refer_emergency`). Cases cover adult primary care, children, diabetes, blood pressure, asthma, infectious disease, mental health and crisis, medicines, prevention, older adults, disability and access barriers. Devanagari, Roman Hindi and Hinglish prompts are included.

## Localization and interpretation

- India ERSS **112** covers medical emergencies. Do not copy UK 999/111 into India-facing responses. Availability and arrival times depend on local services; no response-time guarantee is made.
- Tele-MANAS **14416** / **1-800-891-4416** are verified in a February 2026 Government of India source. A March 2026 MoHFW release independently confirms 14416 and round-the-clock counselling. In imminent danger, counselling is additional support and must not delay 112 or emergency care.
- Reference labels are evaluation policy authored for the stated scenario. A `refer_phc` label means professional assessment is needed; the response must preserve scenario-specific urgency and escalate if danger signs emerge. These labels are not a universal clinical triage scale.
- Cases avoid individualized doses, invented measurements and unsupported diagnostic certainty. Any prescription guidance should defer to the treating professional or an existing personalized action plan.
- Specific accommodations, transport arrangements and facilities must be checked locally. Disability should not reduce the urgency or quality of care.

## Limits and review needed

- This small suite is a software and response-safety benchmark, not evidence of clinical effectiveness or comprehensive health coverage.
- A qualified clinician should review clinical actions, urgency and contraindications before the cases guide any patient-facing deployment. A Hindi-speaking reviewer should check clarity, cultural fit and equivalence across scripts.
- WHO fact sheets and public-facing guidance do not specify every scenario-specific routing decision. Draft judgments include same-day assessment for blood in a child’s stool, prompt review of a diabetes foot wound, and emergency handling of severe breathlessness. Those judgments need clinical review.
- Medication allergy, poisoning and emergency recognition guidance was localized from NHS content by replacing contact routing with official Indian sources; this does not establish full equivalence of local services.
- Deliberate coverage limits include pregnancy-specific care, individualized prescribing, rare disease, diagnostic thresholds, complete vaccination schedules, and psychiatric diagnosis. Broader health scope does not mean all health topics are covered.
- Older WHO pages remain useful for general safety principles, but source availability and guidance should be rechecked with every clinically meaningful dataset revision.

## Broader AI governance rubric

[Ethics and governance of artificial intelligence for health, WHO, 28 June 2021](https://www.who.int/publications/i/item/9789240029200) provides broad principles for health AI. [Section 5 of the report](https://iris.who.int/bitstream/handle/10665/341996/9789240029200-eng.pdf) discusses keeping humans in control of medical decisions, protecting privacy and consent, understandable system behavior, accountability, equitable access, and responsiveness over time. These principles support checks for human escalation, honest limitations, privacy and inclusive language in HealthEval. They do not endorse this implementation or establish any numerical pass threshold.

## Sarvam model identity and API check

Verified on **13 September 2026** against current official API documentation and the release log. [Sarvam’s changelog](https://docs.sarvam.ai/changelog) records the retirement of `sarvam-m` in June 2026 and `sarvam-30b` in July 2026; neither should be used as an API candidate or as an alias for another model. Older model announcements and cached documentation can still show their historical availability.

The current [Chat Completion API reference](https://docs.sarvam.ai/api-reference/chat/chat-completions) permits exactly two Sarvam-native models on `POST https://api.sarvam.ai/v1/chat/completions`: `sarvam-105b` and `sarvam-105b-conversations`. The [105B model documentation](https://docs.sarvam.ai/api/getting-started/models/sarvam-105b) describes the former as the reasoning/agent model with a 128K-token context, and the latter as a post-trained conversational variant with a 32K-token context for natural, colloquial Indic chat and voice-agent dialogue. Both cover native, romanized and code-mixed Indian-language input. `sarvam-105b` is also supported on v2; the conversational variant uses v1.

**Workload recommendation:** use `sarvam-105b-conversations` for the default Hindi health chatbot candidate. `sarvam-105b` can be evaluated as a separately identified reasoning comparator. This recommendation follows the vendor’s stated task fit; no source establishes either model’s clinical accuracy or safety. Record the exact requested and returned model IDs and evaluation parameters with every run.

Sarvam’s [Epoch announcement](https://www.sarvam.ai/epoch/summary) says the first 105B checkpoint arrived in February and that updated conversational and work-agent variants were released at Epoch. The announcement does not expose a precise release date in the retrieved text; a chronological claim that one current 105B variant is newer than the other is therefore unverified. The March 6, 2026 [open-source release](https://www.sarvam.ai/blogs/sarvam-30b-105b) describes earlier checkpoints, not the full current API availability.

For v1 request configuration, the current API schema accepts `reasoning_effort` as `low`, `medium`, `high`, or explicit JSON `null` to disable reasoning. Set this value explicitly: the API reference describes a default of `medium`, while the [chat overview](https://docs.sarvam.ai/api-reference-docs/api-guides-tutorials/chat-completion/overview) describes `low`. Both say reasoning can use the completion-token budget. `max_tokens` defaults to 2048; small budgets can yield an empty visible answer and `finish_reason: "length"`. The model page lists plan limits of 4096 / 16384 / 128000 generated tokens for Starter / Pro / Business respectively, with the model context window imposing an additional bound. API authentication can use `api-subscription-key`; the overview also documents bearer authentication for compatible clients. Live requests must verify credentials and account-specific availability.

## Gemini output-budget verification

For short JSON-first responses, Gemini 2.5 Pro now uses `max_output_tokens=4096` and explicit `thinking_budget=512`. Google's [generateContent thinking guide](https://ai.google.dev/gemini-api/docs/generate-content/thinking) documents its valid thinking budget as 128–32768, with dynamic thinking when omitted. A live run with the earlier dynamic setting returned one truncated JSON fence; that observation alone does not establish its exact cause because the original call did not retain finish reason or thinking-token usage. The configuration change is followed by a new 30-case Gemini run.
